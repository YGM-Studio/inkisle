# Technical Plan

## Foundation

InkIsle should be built as a product layer on top of Astro + Vite.

Reasons:

- Astro is static-first and can pre-render HTML.
- Astro has native Markdown and MDX support.
- Content collections, RSS, sitemap, i18n, and adapters provide a strong base.
- SSR or edge rendering can be added later through adapters, but it is not the default path.

Vinext is not the first choice for this project because InkIsle's first requirement is static-first publishing and pre-rendered HTML, not a Next.js-like application runtime.

## Content Structure

Source content uses a main-language-without-prefix convention. Translated content uses language-prefixed directories.

```text
content/posts/my-post.md
content/en/posts/my-post.md
content/pages/about.md
content/en/pages/about.md
```

Build output should include language prefixes. If the main language is Chinese:

```text
/zh/posts/my-post
/en/posts/my-post
```

Default post URLs do not include dates. Dates are used for sorting only.

```text
/posts/my-post
```

The actual output route may add the language prefix according to site configuration.

## Project Exposure Levels

InkIsle has two starter shapes in V0:

```text
starters/content-only/  # default user project
starters/default/       # full Astro project and internal renderer source
```

The default `inkisle init` should create a lightweight content project with Markdown, `package.json`, npm scripts, optional config, and optional static assets. It should not copy Astro pages, layouts, components, or Vite configuration as editable source.

Advanced users can request the full project:

```bash
inkisle init my-site --full
```

In a content project, `npm run dev`, `npm run build`, and `npm run preview` should call `inkisle dev`, `inkisle build`, and `inkisle preview`, which run the internal full Astro renderer against the current working directory as the site root. The renderer reads content from the user's `content/` directory, static assets from the user's `public/` directory when present, and configuration from `inkisle.config.*` when present.

This keeps Astro as the implementation foundation while keeping the product surface small.

## Frontmatter

The builder should only require `title`.

The CLI should generate recommended metadata:

```yaml
---
title: "Post title"
date: 2026-05-02
updated: 2026-05-02
summary: ""
tags: []
category:
draft: true
---
```

Rules:

- `title` is required.
- `date` is generated by the CLI and used for sorting.
- `slug` is generated from the file name by default.
- Frontmatter `slug` can override the generated slug.
- `category` is optional.
- `tags` are optional.
- Markdown is the default authoring format.
- MDX can be supported, but it is not the first priority.

## Multilingual Model

The main language is written directly in:

```text
content/posts/
content/pages/
```

Translations live in:

```text
content/{lang}/posts/
content/{lang}/pages/
```

Translation is not a V0 system feature. InkIsle should provide clear guidance for AI agents so they know where translated files should be written.

If a post does not have a translated version, the behavior should be configurable:

- Redirect or link back to the main-language URL.
- Hide the post in that language.

## AI-Friendly Outputs

InkIsle should support three AI-friendly output types.

### Raw Markdown

Default: disabled.

When enabled:

```text
/raw/posts/my-post.md
```

### Structured JSON

Default: generate full-site index.

```text
/api/posts.json
```

Optional per-post JSON:

```text
/api/posts/my-post.json
```

### llms.txt

Default: generate a simple index.

Do not generate `llms-full.txt` by default in V0, because full-text output can become large and increases scraping exposure.

## Search

V0 should use static search.

Default indexed fields:

- Title.
- Summary.
- Tags.
- Plain text body.

Code blocks, raw HTML, and custom component content can be revisited later.

Server-side search is out of scope for V0 because it introduces runtime, adapter, cache, index refresh, permission, and cost concerns.

## Theme Boundary

V0 themes should focus on CSS and layout.

Principles:

- Content does not depend on themes.
- Features do not depend on themes.
- Themes control visual presentation and layout.
- The default theme should be a personal blog.

Theme sources:

- Local theme directory.
- npm package theme.
- Built-in default theme.

Component or slot override can be added later. To keep that path open, internal implementation should keep clear component boundaries:

- `PostList`
- `PostLayout`
- `TagPage`
- `SearchPage`
- `FeedGenerator`

## Pages

Page-like content should be supported without turning InkIsle into a CMS.

Supported forms:

- Markdown pages.
- Astro or HTML pages only in full project mode.

Astro/HTML custom pages should have higher priority than Markdown pages when routes conflict.

Whether page-like content participates in the theme system should be configurable.

## CLI

V0 commands:

```bash
inkisle init [dir]
inkisle init [dir] --full
inkisle new post
inkisle new page
inkisle dev
inkisle build
inkisle preview
```

Later commands:

```bash
inkisle eject
inkisle theme
inkisle translate
inkisle doctor
```

The CLI should make InkIsle feel like a product, not just an exposed Astro project.

Default command behavior:

- `init` creates lightweight content projects with `package.json` and npm scripts.
- `init --full` copies the full Astro project.
- `dev`, `build`, and `preview` run against the current content repository unless already inside a full project.
- `new` writes Markdown into the current content repository.

## Deployment Targets

Must support:

- Cloudflare Pages.
- Cloudflare Workers.
- Self-hosted servers.
- GitHub Pages.

May support:

- Vercel.
- Netlify.
- Docker static hosting.

InkIsle should not bind itself to one cloud provider.

## SSR Strategy

Default: static output with pre-rendered HTML.

SSR is not a V0 priority. Possible future SSR use cases:

- Comments.
- Login state.
- Dynamic preview.
- Runtime personalization.

For V0, comments should only use a unified mount slot. Built-in comment providers can come later.
